# React Flow API audit for the Roadmap canvas

**Scope.** Official React Flow documentation reviewed on 2026-09-03: the supplied [components](https://reactflow.dev/api-reference/components), [hooks](https://reactflow.dev/api-reference/hooks), [types](https://reactflow.dev/api-reference/types), and [utils](https://reactflow.dev/api-reference/utils) indexes, plus the directly relevant API pages linked below. The project uses `@xyflow/react` 12.11.3.

## Finding summary

The Roadmap canvas already uses several appropriate first-party primitives: `ReactFlow`, `Background`, `Panel`, `Handle`, `BaseEdge`, `EdgeLabelRenderer`, `getSmoothStepPath`, `applyNodeChanges`, `applyEdgeChanges`, `Connection`, `MarkerType`, `Position`, and `useStore`. The review found three clear or partial overlaps with documented React Flow functionality, and two important custom areas that should remain custom.

| Assessment | Project implementation | React Flow facility | Recommendation |
| --- | --- | --- | --- |
| Clear overlap | `FloatingEdge` manually places the selected-edge delete button through `EdgeLabelRenderer`, absolute positioning, a transform, and explicit `selected` gating ([FloatingEdge.tsx](../../src/features/roadmap/graph/FloatingEdge.tsx#L73-L99)). | [`<EdgeToolbar />`](https://reactflow.dev/api-reference/components/edge-toolbar) takes an edge id and the calculated `x`/`y`, is selected-only by default, and keeps the content unscaled. | Replace the placement/gating wrapper with `EdgeToolbar`. Retain the button and domain deletion callback. |
| Partial overlap | `nodeRect` reads `nodeLookup`, `measured`, and `internals.positionAbsolute` from `ReactFlowState`, with a bespoke selector and equality comparison ([FloatingEdge.tsx](../../src/features/roadmap/graph/FloatingEdge.tsx#L16-L50)). | [`useInternalNode()`](https://reactflow.dev/api-reference/hooks/use-internal-node) exposes the public `InternalNode` for an id; [`useNodesInitialized()`](https://reactflow.dev/api-reference/hooks/use-nodes-initialized) exposes measurement readiness. | Prefer `useInternalNode(source)` / `useInternalNode(target)` when they supply the needed geometry. ## Documented facilities relevant to the canvas

### Components

- [`<Controls />`](https://reactflow.dev/api-reference/components/controls) supplies zoom, fit-view, and interactivity-lock controls; [`<ControlButton />`](https://reactflow.dev/api-reference/components/control-button) extends that panel. Use it if the roadmap later adds those viewport controls instead of building them independently.
- [`<Panel />`](https://reactflow.dev/api-reference/components/panel) positions UI over the viewport; the existing top-right action bar already uses it. [`<MiniMap />`](https://reactflow.dev/api-reference/components/minimap) provides a graph overview and current-viewport indicator if the roadmap needs navigation at scale.
- [`<NodeToolbar />`](https://reactflow.dev/api-reference/components/node-toolbar) and [`<EdgeToolbar />`](https://reactflow.dev/api-reference/components/edge-toolbar) provide non-scaling, selection-aware action surfaces. [`<ViewportPortal />`](https://reactflow.dev/api-reference/components/viewport-portal) is instead for custom elements that must pan and zoom with graph coordinates.
- [`<NodeResizer />`](https://reactflow.dev/api-reference/components/node-resizer) and [`<NodeResizeControl />`](https://reactflow.dev/api-reference/components/node-resize-control) cover interactive node resizing. They do not replace the roadmap's title-based minimum sizing policy.

### Hooks, types, and utilities

- [`useReactFlow()`](https://reactflow.dev/api-reference/hooks/use-react-flow) exposes the typed instance for graph queries, node/edge updates, and viewport operations without a reactive subscription. [`useNodesState()`](https://reactflow.dev/api-reference/hooks/use-nodes-state) and [`useEdgesState()`](https://reactflow.dev/api-reference/hooks/use-edges-state) are controlled-flow helpers; this project correctly uses the lower-level [`applyNodeChanges()`](https://reactflow.dev/api-reference/utils/apply-node-changes) and [`applyEdgeChanges()`](https://reactflow.dev/api-reference/utils/apply-edge-changes) because it deliberately filters deletion changes and adds domain-specific edge appearance rules.
- [`getConnectedEdges()`](https://reactflow.dev/api-reference/utils/get-connected-edges), [`getIncomers()`](https://reactflow.dev/api-reference/utils/get-incomers), and [`getOutgoers()`](https://reactflow.dev/api-reference/utils/get-outgoers) are the first choice for future UI-only traversal over the rendered graph. They must not replace server-owned Dependency validation, prerequisite blocking, or persistence.
- [`addEdge()`](https://reactflow.dev/api-reference/utils/add-edge) validates duplicate/invalid rendered edges; [`reconnectEdge()`](https://reactflow.dev/api-reference/utils/reconnect-edge) updates a rendered edge. Neither replaces the API's authoritative creation or validation of a Dependency.
- [`getNodesBounds()`](https://reactflow.dev/api-reference/utils/get-nodes-bounds) and [`getViewportForBounds()`](https://reactflow.dev/api-reference/utils/get-viewport-for-bounds) cover client/server fit-transform calculations. The existing initial `fitView` is already the direct built-in solution.
- [`IsValidConnection`](https://reactflow.dev/api-reference/types/is-valid-connection) can provide immediate client feedback during connection creation, but server validation remains necessary for acyclicity and the Roadmap's blocking consequences. [`useConnection()`](https://reactflow.dev/api-reference/hooks/use-connection) can support handle-level feedback during that interaction.
- [`OnBeforeDelete`](https://reactflow.dev/api-reference/types/on-before-delete) is asynchronous and can cancel or replace a proposed node/edge deletion. It is relevant if deletion orchestration is later consolidated, but it does not eliminate the product confirmation dialog or server-side Dependency deletion.

## Non-duplicates: retain the custom code

- The dynamic endpoint selection in `floatingEdgeGeometry`, `nearestSide`, and `sideAnchor` ([geometry.ts](../../src/features/roadmap/graph/geometry.ts#L62-L106)) has no packaged React Flow component or utility replacement. React Flow's own [Floating Edges example](https://reactflow.dev/examples/edges/floating-edges) describes this as an example implementation whose source and target positions are calculated dynamically. `getSmoothStepPath()` only produces a path after those endpoints are chosen; the project already uses it correctly.
- `layoutRoadmapGraph` remains appropriately custom/Dagre-backed. The documentation presents layout integrations and examples, not a built-in automatic layout engine. The Roadmap-specific size calculation and grid alignment encode visual policy and should stay outside React Flow.
- The roadmap's `Dependency` semantics (server validation, cyclicity, student impact preview, confirmation, and persistence) are domain behavior, not React Flow graph-state behavior. React Flow utilities may improve editor responsiveness, but must not become the authority for that behavior.

## ADR-ready conclusion

Adopt React Flow's `EdgeToolbar` and public `useInternalNode` surface where compatible, and remove the redundant drag-stop rounding only after an interaction test proves the snapped position is delivered. Preserve custom floating-edge geometry, Dagre layout, and the server-authoritative Roadmap/Dependency rules. This bounds React Flow to canvas mechanics while retaining the product's pedagogical semantics.
